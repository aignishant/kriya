# 4.3 — The promotion that was not verified

## One-line answer

Today's deliberate failure is a promotion where **every gate was green and the change never arrived**: the
artifact was right, the configuration matched, the previous environment was healthy, the record was written —
and the process serving traffic was the old one, because nothing compared the ledger to reality.

---

## The story

🎬 **The scene.** A restaurant kitchen, and a specials board changed for the evening service.

The chef writes the new specials on the board in the pass. The front-of-house manager reads it, briefs the
waiting staff, updates the printed inserts, and the till is reprogrammed. Four steps, all completed, all
confirmed.

😬 **The naive fix** is not a shortcut — it is that nobody walks into the dining room and looks at a table.

💥 **Why it fails.** The dining room has a second board, on the wall, that is a copy of the specials for
customers to read while they wait. It has been there for years. It is nobody's job because it has never needed
one.

Every one of the four steps was completed correctly. **The room the customers are sitting in still says
yesterday's specials**, and the first person to notice is a customer ordering something that does not exist.

💡 **The insight.** **A process that confirms each of its own steps is not the same as a process that checks
the outcome.** Every internal confirmation can be true while the thing the world sees is unchanged — and the
only check that catches it is one that looks at the world rather than at the process.

---

## The idea in plain language

Section 2 built four things and every one of them is honest work:

- `build.sh` refuses on a dirty tree;
- `release.sh` refuses on a missing build or a missing config;
- `gate.sh` checks four conditions and refuses on any of them;
- and the release ledger records what was decided.

**All four can pass while nothing changes.**

The gap is that every one of them reasons about **records and files**. Not one of them asks the running
service anything. So the failure mode is:

| Step | Reports | Reality |
| --- | --- | --- |
| build | `build-7f3e9c1a8b04` | ✅ correct |
| gate | four conditions green | ✅ correct |
| release | `r012` recorded for staging | ✅ correct |
| run | the command was issued | ❌ **the port was already held; the new process exited** |
| verification | — | **there was none** |

**The deploy "succeeded" and the old code is still serving.** Every artifact of the process says the change
shipped.

This is the same shape as five previous days, and by now it should be irritating rather than surprising:

| Day | The thing that was wrong | Every cheap signal said |
| --- | --- | --- |
| 5 | rotation freed no disk | fine |
| 6 | the kernel killed the process | fine |
| 7 | connections exhausted | fine |
| 8 | the certificate had expired | `200` |
| 9 | the configuration was the wrong environment's | `200`, healthy, no errors |
| **10** | **the deploy never took** | **every gate green, the record written** |

**The property they share, finally stated:** *the signals that are cheap to check are the ones that stay
green*, because a cheap signal is one that examines something nearby — the process, the file, the record — and
the failure is always one step further out.

**The counter-measure is the same every time: check the outcome from outside, with an independent source.**
[4.1](4.1-one-artifact-three-releases.md) built that source. This part uses it as a gate.

---

## Why Kriya needs it

**Day 13's pipeline** will run a deploy step, and this is the step that must follow it.

**Day 18 and Day 19** make the response automatic: a verification that fails should roll back rather than
notify.

**Day 41's rolling update** has an internal version of this — a readiness gate per replica — and it exists
because the same failure at fleet scale is a rollout that reports success with three of nine replicas updated.

**Day 55's GitOps** inverts it: instead of pushing and verifying, a controller continuously compares desired
state against actual state and corrects the difference. **That is this check, running forever**, and it is why
drift detection is the central idea of that phase.

**Day 74's alerts** and **Day 79's runbook** are where a failed verification becomes somebody's problem at a
particular hour.

## The mechanism

The day's red gate. **Green, red, green** — and the red is produced by a completely ordinary accident.

```bash
# lab/promote_and_verify.sh - the full pipeline, ending with a check of reality.
set -u
TARGET="${1:?usage: promote_and_verify.sh <environment>}"
ROOT="$(git rev-parse --show-toplevel)"
LAB="$ROOT/days/day-010-environments-and-promotion/lab"

echo "== 1. gate =="
bash "$LAB/gate.sh" "$TARGET" || { echo "STOPPED at the gate" >&2; exit 1; }

echo "== 2. build + release =="
BUILD=$(bash "$LAB/build.sh") || exit 1
RELEASE=$(bash "$LAB/release.sh" "$BUILD" "$TARGET") || exit 1
echo "   recorded $RELEASE = $BUILD in $TARGET"

echo "== 3. run =="
bash "$LAB/run.sh" "$RELEASE" > "/tmp/pulse-$TARGET.log" 2>&1 &
sleep 4

echo "== 4. verify =="
bash "$LAB/verify.sh" "$TARGET" || {
  echo "DEPLOY FAILED: the record says $RELEASE and the service disagrees" >&2
  echo "               the previous release is still serving; nothing was rolled back" >&2
  exit 1
}
echo "DEPLOY OK: $TARGET is running $RELEASE ($BUILD)"
```

**Line by line:**

- Four numbered steps, each printed, so a failure is attributable to a stage by reading the output rather
  than by reasoning about it.
- `|| { …; exit 1; }` after **every** stage. A pipeline that continues past a failed stage is a pipeline that
  reports the wrong cause.
- **Step 4 is the whole point.** Steps 1–3 are the honest work from section 2, and without step 4 the script
  would print nothing but success in the failure below.
- The failure message says two things: what disagreed, **and what state the system is now in** — *"the
  previous release is still serving; nothing was rolled back"*. An operator reading a failure at 3am needs the
  second sentence more than the first, and Day 19 is where the rollback becomes automatic.
- `sleep 4` before verifying: the service needs to bind before it can be asked. **A verification that runs too
  early reports a failure that is not one**, which is how verification steps get removed for being flaky.

Run it green:

```bash
cd "$(git rev-parse --show-toplevel)"
LAB=days/day-010-environments-and-promotion/lab
pkill -f 'pulse.api:app' 2>/dev/null; sleep 1
BUILD=$(bash "$LAB/build.sh"); R=$(bash "$LAB/release.sh" "$BUILD" dev)
bash "$LAB/run.sh" "$R" > /tmp/pulse-dev.log 2>&1 &
sleep 4
bash "$LAB/promote_and_verify.sh" staging ; echo "exit=$?"
```

**Line by line:**

- `dev` is deployed and running first, because `gate.sh`'s conditions 1 and 4 require it
  ([2.3](../02-promotion/2.3-the-promotion-gate.md)).
- `pkill` and `sleep 1` at the start so a leftover process from an earlier part cannot hold a port — **which
  is exactly the accident about to be staged deliberately.**

```text
== 1. gate ==
gate ok  [1,2]: dev runs build-14a1dcd2f0b4, which is the current build
gate ok  [3]: dev and staging declare the same settings
gate ok  [4]: dev is healthy on :8000
GATE GREEN: build-14a1dcd2f0b4 may be promoted to staging
== 2. build + release ==
   recorded r014 = build-14a1dcd2f0b4 in staging
== 3. run ==
== 4. verify ==
ok    environment staging
ok    build_id    build-14a1dcd2f0b4
ok    release_id  r014
VERIFY GREEN: staging is running exactly what the ledger says
DEPLOY OK: staging is running r014 (build-14a1dcd2f0b4)
exit=0
```

### Now make it red, with an ordinary accident

The failure is **a process already holding the port** — Day 7's `EADDRINUSE`
([Day 7, 1.4](../../../day-007-networking-for-operators/parts/01-addresses-and-ports/1.4-the-port-that-was-already-in-use.md)),
which is the single most common way a deploy silently does not take.

```bash
cd "$(git rev-parse --show-toplevel)"
LAB=days/day-010-environments-and-promotion/lab

echo '### stage the accident: an OLD release is already serving staging ###'
pkill -f 'pulse.api:app' 2>/dev/null; sleep 1
BUILD=$(bash "$LAB/build.sh")
OLD=$(bash "$LAB/release.sh" "$BUILD" staging)
bash "$LAB/run.sh" "$OLD" > /tmp/pulse-staging-old.log 2>&1 &
sleep 4
echo "staging is serving $OLD"

echo '### dev must be up for the gate ###'
DEVR=$(bash "$LAB/release.sh" "$BUILD" dev)
bash "$LAB/run.sh" "$DEVR" > /tmp/pulse-dev.log 2>&1 &
sleep 4

echo '### now promote again: the port is taken, so the new process dies ###'
bash "$LAB/promote_and_verify.sh" staging ; echo "exit=$?"

echo '### what the new process actually said ###'
tail -3 /tmp/pulse-staging.log
```

**Line by line:**

- The old release is started **first and left running**, which is precisely the state a real deploy meets when
  a stop step failed, a supervisor restarted the old container, or a `pkill` pattern matched nothing.
- The second `release.sh` for staging creates a **new** release ID with the same build — so the artifact is
  identical and only the release differs. **That is deliberate**: it isolates the failure to "the deploy did
  not take" rather than confusing it with an artifact difference.
- `tail -3` on the *new* process's log, to see the actual error rather than inferring it.

```text
### stage the accident: an OLD release is already serving staging ###
staging is serving r015
### dev must be up for the gate ###
### now promote again: the port is taken, so the new process dies ###
== 1. gate ==
gate ok  [1,2]: dev runs build-14a1dcd2f0b4, which is the current build
gate ok  [3]: dev and staging declare the same settings
gate ok  [4]: dev is healthy on :8000
GATE GREEN: build-14a1dcd2f0b4 may be promoted to staging
== 2. build + release ==
   recorded r017 = build-14a1dcd2f0b4 in staging
== 3. run ==
== 4. verify ==
ok    environment staging
ok    build_id    build-14a1dcd2f0b4
RED   release_id  recorded=r017 running=r015
VERIFY RED: staging does not match its release record
DEPLOY FAILED: the record says r017 and the service disagrees
               the previous release is still serving; nothing was rolled back
exit=1
### what the new process actually said ###
ERROR:    [Errno 10048] error while attempting to bind on address ('127.0.0.1', 8001):
only one usage of each socket address (protocol/network address/port) is normally permitted
```

**Read the verify block.** `environment` matches. **`build_id` matches** — the artifact is identical, so
[2.3](../02-promotion/2.3-the-promotion-gate.md)'s condition 2 would have passed even if it had been checked
against the running service. Only `release_id` disagrees, and it is the field that exists precisely because
an artifact identity is not enough
([2.2](../02-promotion/2.2-build-release-run.md)).

**Every gate was green. The record was written. The change did not arrive.**

Now restore and confirm green:

```bash
cd "$(git rev-parse --show-toplevel)"
LAB=days/day-010-environments-and-promotion/lab
pkill -f 'pulse.api:app'; sleep 2
netstat -ano | grep -E ':(8000|8001|8002).*LISTENING' || echo "ports clear"
BUILD=$(bash "$LAB/build.sh"); D=$(bash "$LAB/release.sh" "$BUILD" dev)
bash "$LAB/run.sh" "$D" > /tmp/pulse-dev.log 2>&1 & sleep 4
bash "$LAB/promote_and_verify.sh" staging ; echo "exit=$?"
pkill -f 'pulse.api:app'
```

**Line by line:**

- `pkill` then **`netstat` to verify**, not to trust — the same discipline as every cleanup in this
  curriculum, and here it is load-bearing because the whole failure was a held port.
- The green run afterwards is not optional: **a drill that only goes red has proved the failure, not the
  fix.**

```text
ports clear
...
DEPLOY OK: staging is running r019 (build-14a1dcd2f0b4)
exit=0
```

## When it breaks

**The port that was held.** The failure above, in its natural habitat:

```text
$ kubectl rollout status deployment/pulse
Waiting for deployment "pulse" rollout to finish: 1 old replicas are pending termination...
$ # ...and it waits, and the pipeline times out, and somebody re-runs it
```

**What it says:** a rollout that has not completed.
**What it actually means:** in Kubernetes this particular accident is largely prevented — the platform owns
the port and will not start a new pod on top of an old one. **Which is worth saying plainly: much of what this
part builds by hand is what an orchestrator gives you**, and Day 34 onwards is where you stop writing it.
**What does not go away** is the need to verify the outcome: a rollout can report success with the old image
if the tag did not move ([2.4](../02-promotion/2.4-the-rebuild-that-promoted-something-different.md)), and a
`ConfigMap` change can be recorded and never reach a running pod
([Day 9, 1.2](../../../day-009-configuration-and-secrets/parts/01-configuration/1.2-the-environment-is-the-interface.md)).
**The mechanism changes; the check does not.**

**The verification that ran too early.** The flaky gate:

```text
== 4. verify ==
VERIFY RED: staging is not answering on :8001
DEPLOY FAILED: the record says r021 and the service disagrees
```

...on a deploy that was, four seconds later, entirely fine.

**What it says:** the service was not answering.
**What it actually means:** the check ran before the process finished starting. **The deploy succeeded and the
verification failed**, which is the worst possible outcome for a gate: it trains people to re-run it, then to
ignore it, then to remove it.
**The smallest fix:** poll until it answers, with a bounded overall deadline, rather than sleeping a fixed
interval ([Day 7, 4.3](../../../day-007-networking-for-operators/parts/04-timeouts/4.3-the-deadline-that-bounds-the-whole-call.md)).
**Why a fixed `sleep` is in the lab anyway:** it is the honest starting point, and the `TODO(me)` to replace it
with a bounded poll is in the hub. **A flaky gate is worse than no gate**, and this is the most likely way
this one becomes flaky.

**The verification that verified the wrong instance.** The one that gets subtler with scale:

```text
ok    release_id  r022
$ # ...and eight of the nine replicas are still on r021
```

**What it says:** the release matches.
**What it actually means:** the request went to whichever replica the load balancer picked, and it happened to
be an updated one. **A single `curl` samples a fleet; it does not describe one**
([4.1](4.1-one-artifact-three-releases.md)).
**The smallest fix:** ask every replica, or — better — read the identity from a metric with a label, so the
question is *"what is the set of release IDs currently live"* rather than *"what did one request see"*
(Day 62).
**Why this is the natural next failure:** today `pulse` is one process, so a single request is a complete
answer. That stops being true on Day 41, and the check has to change shape at the same moment.

**The verification that had nothing to compare.** The vacuous check, one last time:

```text
ok    environment  
ok    build_id     
ok    release_id   
VERIFY GREEN: staging is running exactly what the ledger says
```

**What it says:** three matches.
**What it actually means:** both greps returned nothing — the JSON format changed, or the endpoint returned an
error body — and **empty equals empty**. The gate is green because it compared two absences.
**The smallest fix:** refuse when any field is empty on either side, before comparing.
**Why this is the seventh time:** Day 0's `./o check`, Day 9's empty allowlist, Day 9's leak gate with no
credential set, Day 10's parity check with a missing file, and now this. **Every check built on comparison has
this failure**, the fix is always "assert there was something to compare", and by now it should be the first
thing you look for in anybody's check — including your own.

## In production

**What a professional writes instead of the teaching version.** The verification is a **step in the deployment
with an automatic response**: if it fails, the deployment is marked failed and the previous release is
restored, without a human. That is Day 19's rehearsed rollback wired to Day 18's deployment strategy, and the
reason it must be automatic is that this failure happens at 3am to somebody who is not reading a pipeline log.
The check itself is broader than three fields: it asserts identity, then makes one representative request and
asserts the *shape* of the answer, because a service can be running the right release and be wrong in a way
identity cannot see.

**What degrades at scale.** From "ask the service" to "ask every replica, and agree on what a partial answer
means". With nine replicas a deploy is not a step but a *transition*, and during it the correct answer is
"both release IDs are live". Verification becomes a statement about a distribution over time — *"all replicas
report the new release within a bounded period"* — which is exactly what a rollout controller does, and is why
Day 41's rolling update subsumes this script rather than extending it.

**The failure that only shows with real traffic.** A deploy that took, verified correctly, and is wrong in a
way identity cannot express: the new release is running, reports itself accurately, and is slower or subtly
incorrect under load — which is
[3.3](../03-what-production-promises/3.3-the-staging-environment-that-lied.md)'s p99, arriving after a
verification that passed. **Verification proves arrival, never correctness**, and the things that prove
correctness are a canary, a comparison against the previous version's error rate, and a rollback that a signal
can trigger.

**The review comment a senior engineer leaves.** *"The deploy job ends when `kubectl apply` returns, which
only means the API server accepted the object. Add `rollout status` with a deadline, and then a smoke check
that asks the service what release it is running and compares it with what we just recorded. The failure I
have seen twice is a deploy that was recorded and never took — everything is green and the change is not
there, and the first detector is somebody asking why their fix has not shipped."*

**The signal you would alert on.** **A deployment whose verification failed** — and it should page, because it
is both urgent and actionable, and because the system is in a known-inconsistent state: the ledger says one
thing and reality is another. Beyond that, the same two disagreement alerts from
[4.1](4.1-one-artifact-three-releases.md): more than one release ID live for longer than a rollout should
take, and a release ID running that no record mentions. What you would **not** do is alert on the
verification *passing*, and what you must **not** do is have the verification only log — a check whose only
output is a log line during an automated deploy is a check nobody reads.

**Blast radius.** This part deliberately puts the system into the failure state it is teaching: an old release
serving while a new one is recorded. Worst case: the drill is left half-finished, an old process keeps a port,
and the *next* part's measurement is wrong — Day 8's trap 7, which is exactly the accident being staged. What
bounds it: every process binds loopback only, the drill's last block kills everything and **verifies with
`netstat` rather than trusting `pkill`**, and the checklist requires the ports to be confirmed clear and
`git diff pulse/` to be empty. The scripts themselves only read and record; **nothing in this day can delete
data or change anything outside `lab/`.** Who can trigger it: you.

**Cost.** `0` model calls, `0` tokens, `0` CI minutes, `0` new packages, `0` external network. RAM: up to
**three** uvicorn processes at roughly 60 MB — about 180 MB peak (Addendum 02 §3). Disk: several small JSON
records and three logs in `/tmp`.

**The interview question.** *"Your deploy pipeline says success. How do you know the change is live?"* The
answer that shows the distinction between a process and an outcome: *"Because something asked the running
service, not because the pipeline finished. Every step of a deploy can confirm itself correctly while nothing
changes — the classic is a new process failing to bind because the old one still holds the port, so the record
says the release shipped and the old code is serving. The check is to have the service report its own release
identity and compare that against what was just recorded, as a step in the deploy, with a rollback on failure
rather than a log line. Two things I watch for: the check running before the service has finished starting,
which makes it flaky and gets it deleted; and the check comparing two empty strings when a field is missing,
which makes it pass vacuously. And with more than one replica a single request samples the fleet rather than
describing it, so at that point it has to become 'all replicas report the new release within a deadline'."*

```bash
cd "$(git rev-parse --show-toplevel)"

```
