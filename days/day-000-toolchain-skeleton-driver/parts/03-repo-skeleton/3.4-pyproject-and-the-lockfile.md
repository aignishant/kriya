# 3.4 — `pyproject.toml` and the lockfile

## One-line answer

`pyproject.toml` is the one file where **every tool in this project is configured** — dependencies,
linter, formatter, test runner, packaging — so that a setting has exactly one home, and `uv.lock`
sits beside it recording what those declarations actually resolved to.

---

## The story

🎬 **The scene.** Someone is trying to work out why the formatter keeps fighting them. It reformats a
file, they change it back, it reformats again. They go looking for the configuration.

😬 **The naive fix.** They find a config file at the repository root and change the line width. No
effect. They find a second config file in a subdirectory and change it there too. Still no effect.
They add a comment to disable the formatter on that line, which works, and move on with a small,
permanent grievance.

💥 **Why it fails.** There were three places that could configure the formatter, and the tool reads
them in a documented order of precedence. The one that was actually winning was the third, which
nobody had opened, because nobody knew to look. The setting was not hard to change — it was hard to
*find*, which is a different problem and a worse one, because searching has no obvious end.

💡 **The insight.** The cost of configuration is rarely in the values. It is in **the number of
places a value could be**. Every additional location multiplies the search space for everyone,
forever. One file that is always the answer beats five files that are each sometimes the answer.

---

## The idea in plain language

**`pyproject.toml` is a standardised manifest for a Python project.** Two things make it useful, and
they are separate:

1. It is the **standard** place to declare what a project is and what it depends on — its name,
   version, supported Python range, and dependencies.
2. It carries a `[tool.<name>]` table for **any tool that wants one**. The linter reads
   `[tool.ruff]`, the test runner reads `[tool.pytest.ini_options]`, `uv` reads `[tool.uv]`. Each
   tool gets a private room in a shared house.

That second property is why this file matters more than it looks. Before it, every tool had its own
dotfile, and a repository root accumulated a dozen of them. Now the default answer to "where is X
configured?" is: one file, look for the table with X's name.

**TOML** is the file's format — a configuration language designed to be unambiguous to read. Two
pieces of syntax appear here: `[section]` starts a table, and `[[section]]` (double brackets) means
*an item in a list of tables*, which is what `uv.lock` uses for its packages
([1.3](../01-the-toolchain/1.3-uv-the-one-binary.md)).

### The division of labour with `uv.lock`

This is the distinction from [1.3](../01-the-toolchain/1.3-uv-the-one-binary.md), now made concrete
in two files you can open:

| | `pyproject.toml` | `uv.lock` |
| --- | --- | --- |
| Answers | what do we want? | what did we get? |
| Author | you | `uv` |
| Contains | direct dependencies, tool config | every package, transitive included, with hashes |
| Hand-edited | **yes** | **never** |
| Committed | yes | **yes** |
| Read by | you and every tool | `uv`, on every `uv run` |

**Both are committed.** The manifest without the lock is a wish; the lock without the manifest is a
result with no stated intent. You need both to answer "what was supposed to happen, and what actually
happened?" — a pairing that recurs throughout this plan: desired state and observed state, Day 56's
entire subject.

---

## Why Kriya needs it

Day 14 is *"Quality gates — lint, format, types, tests, and a gate that refuses rather than warns."*

A gate is only meaningful if everyone's tools are configured identically — otherwise the gate is
testing the reviewer's laptop rather than the code. Because line length, lint rules and test markers
all live in this one committed file, `./o check` behaves the same for you, for a teammate, and for CI
on Day 13. **The gate's authority comes from its configuration being shared**, and that is a property
of this file rather than of the gate itself.

## The mechanism

The file as it stands on Day 0. **Comments are elided here for readability, and two tables are
omitted** — `[build-system]` and `[tool.hatch.build.targets.wheel]`, which describe how to build this
project into a distributable package. They sit there unused today because `[tool.uv] package = false`
tells `uv` to ignore a declared build system, and they become live on Day 3. Open the real file
alongside this and read the comments; they carry the *why* that this excerpt strips out.

```toml
[project]
name = "kriya"
version = "0.1.0"
requires-python = "==3.12.*"
dependencies = []

[dependency-groups]
dev = [
    "ruff==0.16.4",
    "pytest==9.1.1",
]

[tool.uv]
package = false
link-mode = "copy"

[tool.ruff]
line-length = 100
target-version = "py312"
extend-exclude = ["days/*/lab", "legacy"]

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B", "SIM"]

[tool.pytest.ini_options]
addopts = "-q --strict-markers"
testpaths = ["tests"]
markers = [
    "live: hits a real API, model, cluster or database - skipped by default, never run in CI",
    "cluster: needs a running kind cluster - skipped unless KIND_CLUSTER_NAME is set",
    "slow: takes more than a few seconds",
]
```

**Line by line:**

- `requires-python = "==3.12.*"` — pinned to a *minor* series, not a patch. `3.12.12` and `3.12.13`
  both satisfy it; `3.13` does not. This is the right granularity: patch releases fix bugs and are
  safe to take, minor releases change behaviour. Day 232 (upgrades and migrations) is where you move
  this deliberately rather than by accident.
- `dependencies = []` — **empty, on purpose.** Packages arrive on the day they are first used, never
  up front (Principle 7). An empty list on Day 0 is a statement: this repository currently needs
  nothing to run, and every future addition will be visible in a diff with a reason attached.
- `[dependency-groups]` / `dev = [...]` — tools needed to *develop* the project, not to run it. `uv`
  installs the `dev` group automatically on `uv sync` and `uv run` (*verified against
  `docs.astral.sh/uv/reference/settings/` on 2026-08-24*), which is why `ruff` and `pytest` are
  available without any extra flag. The separation matters later: Day 24's container image installs
  the runtime dependencies and **not** this group, which is a meaningful chunk of image size.
- `ruff==0.16.4`, `pytest==9.1.1` — exact `==` pins, both looked up live on 2026-08-24 and recorded
  in `docs/PACKAGES.md`. Not `>=`. The story in
  [1.3](../01-the-toolchain/1.3-uv-the-one-binary.md) is what `>=` costs.
- `[tool.uv] package = false` — do not build and install this project into its own environment; there
  is no importable code yet ([2.2](../02-the-machine/2.2-onedrive-and-the-hardlink-that-fails.md)).
  **This flips on Day 3.**
- `link-mode = "copy"` — copy from the cache rather than hardlink, as insurance against the
  cloud-sync failure in [2.2](../02-the-machine/2.2-onedrive-and-the-hardlink-that-fails.md).
- `[tool.ruff] line-length = 100` — the maximum line width, used by both the linter and the formatter
  so they cannot disagree with each other. One tool doing both jobs is precisely how the story at the
  top of this page is avoided.
- `target-version = "py312"` — tells the linter which Python to assume, so it can suggest modern
  syntax without proposing something this project cannot run.
- `extend-exclude = ["days/*/lab", "legacy"]` — **`extend-`** is the important prefix: it *adds* to
  the tool's default exclusions rather than replacing them. Plain `exclude` would silently drop the
  sensible defaults, and you would discover that when the linter started reading `.venv`. `days/*/lab`
  is excluded because that is your scratch code — a lab is for experiments, and a linter on an
  experiment is a nuisance rather than a gate.
- `[tool.ruff.lint] select = ["E", "F", "I", "UP", "B", "SIM"]` — which rule families to enforce. Each
  prefix is a whole linter's worth of rules, reimplemented in one tool: `E` pycodestyle errors,
  `F` Pyflakes, `I` isort (import ordering), `UP` pyupgrade (modernising syntax), `B` flake8-bugbear
  (likely bugs), `SIM` flake8-simplify. *Verified against `docs.astral.sh/ruff/rules/` on 2026-08-24.*
  `B` is the one that earns its place fastest — it catches real bugs rather than style, such as a
  mutable default argument.
- `[tool.pytest.ini_options] addopts = "-q --strict-markers"` — options applied to every run. `-q` is
  quiet output. **`--strict-markers` is the one that matters**: without it, a typo in a marker name is
  silently accepted and the test simply never runs the way you intended. With it, an unregistered
  marker is an error. This is the same instinct as the whole day — **fail loudly rather than
  proceeding on a guess**.
- `testpaths = ["tests"]` — where to look for tests, so a bare `pytest` does not go wandering through
  `days/` and `.venv`.
- `markers = [...]` — labels you can attach to tests, each with a description. `live` and `cluster`
  are the load-bearing ones: they let `./o check` skip everything needing a real API or a running
  cluster, so the gate stays fast and offline. Day 13's CI depends on this — a gate that requires a
  cluster is a gate that cannot run in CI.

Confirm the tools actually read it:

```bash
uv run ruff check . && uv run python -m pytest -q -m "not live and not cluster"
```

**Line by line:** `ruff check .` lints the whole tree, honouring `[tool.ruff]` including the
exclusions. `-m "not live and not cluster"` is a marker *expression* — a boolean filter over the
markers declared above — and it is exactly the expression `./o check` uses, so running it by hand
tells you what the gate will say.

Observed on **2026-08-24**:

```text
All checks passed!
```

## When it breaks

Register nothing, then use a marker anyway. With `--strict-markers` on:

```text
'liv' not found in `markers` configuration option
```

**What it says:** an unknown marker.
**What it actually means:** you typed `@pytest.mark.liv` instead of `live`, and the test runner is
refusing rather than guessing. **Without `--strict-markers` this is silent** — the marker is accepted,
the test is not tagged the way you think, and it runs in CI where it was meant to be skipped, hitting
a real API from a pipeline. A typo becoming a runtime behaviour change, with no error, is exactly the
class of failure that strict modes exist to eliminate.

**The smallest fix:** spell it correctly, or register the new marker in `markers`.

The other failure worth meeting is what happens when the manifest and the lock disagree — you edit
`pyproject.toml` by hand and do not re-lock. **There are two flags for this and they are not the
same**, which is worth getting right now because one of them is a trap:

```bash
uv sync --locked
uv sync --frozen
```

**Line by line:**

- `--locked` means *assert that `uv.lock` is up to date with `pyproject.toml`, and fail if it is
  not.* This is the CI flag. A pipeline that silently re-resolves is a pipeline testing something
  other than what you committed.
- `--frozen` means *install from `uv.lock` and do not even look at whether it is current.* It does
  **not** verify anything. It is for situations where you deliberately want the lock as-is — offline
  work, or a container build where re-resolving would be wrong — and reaching for it to make a
  complaint go away silently installs a dependency set that does not match your manifest.

Observed on **2026-08-24**, with `pytest` added to the manifest and the lock left stale:

```text
error: The lockfile at `uv.lock` needs to be updated, but `--locked` was provided.

hint: To update the lockfile, run `uv lock`.
```

The same situation, with `--frozen`, prints no complaint at all and proceeds.

**What it actually means:** the two files disagree. `--locked` gives you the honest answer; `--frozen`
gives you the convenient one. The fix is `uv lock` and then **commit the result** — the lock is part
of the change, not a side effect of it.

**Day 13's pipeline uses `--locked`.** A flag that verifies and a flag that assumes look almost
identical in a CI file, and the difference is whether your build can silently drift.

## In production

**What a professional does differently.** They keep the manifest boring and readable, because it is
read far more often than written. Long inline comments explaining *why* a pin exists — a version held
back for a known incompatibility, a tool setting that looks odd — belong right there next to the
setting, exactly as `[tool.uv]`'s comments do in this repository. A pin with no reason becomes
untouchable within a year, because nobody dares change what nobody understands
([2.2](../02-the-machine/2.2-onedrive-and-the-hardlink-that-fails.md)).

**What degrades at scale.** In a monorepo, one manifest at the root stops working: different services
need different dependency sets, and a single environment containing the union of all of them is both
enormous and constantly conflicted. The way out is per-project manifests with a workspace tying them
together. The symptom that tells you it is time is a resolution that starts taking a long time, or a
dependency conflict between two services that have nothing to do with each other.

**The failure that only shows with real traffic.** Not in this file — but *downstream* of it, and this
is the one worth internalising. A development dependency accidentally declared as a runtime dependency
ships to production inside your image. It is usually harmless and occasionally not: a debugging tool,
a test server, or a package that opens a port. It is bigger, it is more attack surface, and it is in
the SBOM you will generate on Day 15 — where someone will eventually ask why a test framework is in a
production image, and the honest answer will be "nobody noticed the table it was declared in".

**The review comment a senior engineer leaves.** *"`ruff` moved from the dev group to `dependencies`
in this diff. That puts a linter in the production image. Was that deliberate?"*

**The signal you would alert on.** None at runtime. Two gates instead, both on Day 13–15: CI runs
`uv sync --frozen` so a stale lock fails the build, and CI runs the same `ruff` and `pytest`
invocations `./o check` runs locally, so local and remote cannot disagree. **The configuration being
in one committed file is what makes that guarantee possible** — the gate and your laptop read the same
lines.

**Blast radius, stated plainly.** This file configures every tool in the repository, so a mistake here
is repository-wide rather than local: relaxing `select` silently stops enforcing a rule family;
widening `extend-exclude` silently stops checking a directory; changing a pin changes what everyone
installs on their next `uv run`. The bound is that **it is a single committed file, so every change
appears in a diff and is reviewable** — which is exactly why it is better to have one file with real
consequences than five files with diffuse ones.

**Cost:** `0` requests, `0` tokens. Disk: the `dev` group is small; runtime dependencies from Day 3
onward are what grow.

## Check yourself

```bash
uv sync --locked && uv run ruff check . && echo "manifest and lock agree"
```

All three must succeed. If `--locked` fails, your `pyproject.toml` has been edited without re-locking
and CI would reject the change.

**Say out loud, without scrolling up:** *`ruff` and `pytest` are in `[dependency-groups] dev` rather
than `[project] dependencies` — what would break, and what would get worse, if you moved them?*
