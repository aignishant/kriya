# 3.3 — The folder skeleton, decided early

## One-line answer

The repository's folder layout is decided on Day 0 and stays fixed for 236 days — not because the
shape is sacred, but because **a layout decided early is a decision made once, while a layout that
grows organically is a decision remade badly every time somebody adds a file**.

---

## The story

🎬 **The scene.** A project starts as one file. Then a second, for the bits that were getting long.
Then a folder, because there are now six files. Someone adds a script to load the data, at the top
level, because that is where they were standing.

😬 **The naive fix.** Six months later a new person asks where the code that talks to the database
lives. The answer takes four minutes and involves the phrase "well, it depends" twice. Someone
suggests a tidy-up. Everyone agrees it is a good idea. Nobody does it, because moving files breaks
imports and touches every open branch, and there is always something more urgent.

💥 **Why it fails.** No individual decision was wrong. Each file went in a reasonable place *given
where the author was standing at that moment*. The failure is that there was never a place to
consult — so the layout encodes the order files were written in, rather than what they do. And by the
time the cost is visible, the fix has become a large, risky change with no visible benefit.

💡 **The insight.** Structure decided early is nearly free. Structure decided late is a refactor
nobody has time for. **The cost of a layout decision rises sharply with the number of files it would
have to move** — so the correct time to make it is when there are none.

---

## The idea in plain language

A layout is a set of answers to one repeated question: *given a new file, where does it go?* A good
layout answers that in seconds, for someone who has never seen the repository, without asking anyone.

The organising principle here is **separation by lifecycle** — by what changes together, is deployed
together, and is owned together — rather than by file type. That distinction is worth an example,
because "by type" is the layout everyone reaches for first:

| Grouped by type (tempting, worse) | Grouped by lifecycle (this repository) |
| --- | --- |
| `python/`, `yaml/`, `dockerfiles/`, `scripts/` | `pulse/`, `deploy/`, `pipelines/`, `platform_ops/` |
| A change to one service touches four folders | A change to one concern stays in one folder |
| Nothing tells you what the system *does* | The tree describes the system |

Grouping by type means every change is spread across the tree and nothing is co-located with the
thing it belongs to. Grouping by lifecycle means the tree is a map of the system.

### The skeleton, and what each part is for

```text
ops/
├── o                  # the driver script — the one entry point
├── pulse/             # THE SERVICE: api, model wrapper, assistant
├── platform_ops/      # THE PLATFORM CODE: aiops/ · agents/ · mcp/
├── pipelines/         # data + training pipelines, and the CI workflows
├── deploy/            # Dockerfiles, compose, k8s manifests, helm, terraform
├── observability/     # prometheus rules, grafana dashboards, otel config
├── evals/             # model evalsets, LLM evalsets, agent trajectories
├── runbooks/          # one per alert — the 3am documents
├── scripts/           # repo tooling: depth_check.py · tracker.py · trace.py
├── tests/             # pytest
├── days/              # the teaching
└── docs/              # the plan, the addenda, the ledgers, the ADRs
```

**What each directory is for, and why it is separate:**

- `pulse/` versus `platform_ops/` is the single most important boundary in this tree, and it is worth
  understanding now rather than discovering on Day 179. **`pulse/` is the thing being operated;
  `platform_ops/` is the thing doing the operating.** The detectors that watch `pulse` (Day 163), the
  agent that diagnoses its incidents (Day 192), and the tool servers those agents reach through
  (Day 200) are not part of the service — they are a separate system with its own lifecycle, its own
  deployment, and its own failure modes. Mixing them means an outage in your monitoring can be caused
  by a change to the thing being monitored, which is a genuinely bad property.
- `pipelines/` is separate from `pulse/` because batch and serving have different lifecycles. A
  training pipeline runs nightly and may take a long time; the service answers in milliseconds. They
  share a model artifact, not a deployment (Days 93, 109).
- `deploy/` holds everything that describes *how* things run rather than *what* they do. It is
  separate because Day 56 (GitOps) makes this directory the source of truth for the cluster — a
  program will watch it and reconcile reality to it. That only works if it is one identifiable place.
- `observability/` is separate from `deploy/` for a reason people often get wrong: dashboards and
  alert rules are **owned by whoever owns the service**, and change when the service's behaviour
  changes, not when its deployment does. Burying them in `deploy/` makes them infrastructure that
  nobody feels responsible for, which is how dashboards rot.
- `runbooks/` is at the top level rather than inside `docs/` deliberately. These get read at 3am by
  someone under pressure. Making them a first-class directory is a statement about how important they
  are, and Day 79 will require one per alert.
- `evals/` sits apart from `tests/` because they answer different questions. `tests/` asks *is the
  code correct?* and is deterministic. `evals/` asks *is the model's behaviour good enough?* and is
  statistical — it can legitimately be a bit different on each run. Mixing them means either your
  test suite becomes flaky or your evals become too rigid to be honest. Day 104 and Day 148 depend on
  this separation existing.
- `scripts/` is repository tooling, not product code. It never ships in an image.
- `days/` and `docs/` are the memory: the teaching, the plan, the ledgers, and the decisions.

### Why empty folders, today

Every one of these except `scripts/`, `days/` and `docs/` is currently empty, holding only a
`.gitkeep` file — Git records files, not folders, so an empty directory needs a placeholder to exist
in a commit at all.

That is deliberate. **The empty folder is the decision, made visible.** A new file has a place to go
before it exists, so nobody has to invent one under pressure. And the tree tells a reader what this
system is going to be, which is a form of documentation that cannot drift out of date, because it *is*
the thing it describes.

## Why Kriya needs it

Day 56 is *"GitOps — the cluster reconciles itself to the repository."*

GitOps requires a program to watch a directory and continuously make the cluster match it. That is
only coherent if there is exactly one directory that describes the desired state — if manifests are
scattered across the tree, "what should be running?" has no single answer and reconciliation has
nothing to reconcile against.

`deploy/` exists from Day 0 so that Day 56 is a configuration change rather than a reorganisation.

## The mechanism

The skeleton is created by one command, and the `.gitkeep` convention is worth understanding rather
than copying:

```bash
for d in pulse platform_ops/aiops platform_ops/agents platform_ops/mcp \
         pipelines deploy observability evals tests data; do
  mkdir -p "$d" && touch "$d/.gitkeep"
done
```

**Line by line:**

- `for d in … ; do … done` loops over a list of directory names, putting each in turn into the
  variable `d`. A loop rather than ten separate commands, because the ten would drift — someone adds
  a directory and forgets the `.gitkeep`.
- The `\` at the end of the first two lines continues the command onto the next line. It must be the
  **last** character on the line: a single trailing space after it and the shell treats it as an
  escaped space rather than a line continuation, producing a confusing error about an unexpected
  token. This is one of the most annoying five minutes in shell scripting.
- `mkdir -p "$d"` creates the directory. `-p` does two useful things: it creates intermediate
  directories (`platform_ops/aiops` works without creating `platform_ops` first) and it **does not
  fail if the directory already exists**, which makes the whole command safe to run twice. That
  property has a name — *idempotent* — and it is one you will care about a great deal from Day 93
  onward.
- `"$d"` is quoted, as every variable expansion should be
  ([1.2](../01-the-toolchain/1.2-git-and-the-shell-these-docs-assume.md)).
- `touch "$d/.gitkeep"` creates an empty file. `.gitkeep` is **not a Git feature** — Git has no
  special handling for that name at all. It is a convention: since Git records files rather than
  directories, an empty directory cannot appear in a commit, so people put a conventionally-named
  empty file inside to make the directory exist. The name is chosen to be self-explanatory to the
  next human, and that is its entire mechanism.

Verify the result:

```bash
git ls-files | wc -l
```

**Line by line:** `git ls-files` lists every **tracked** file — what is actually in the repository,
as opposed to what happens to be sitting in the folder. `| wc -l` counts the lines. This is the
honest measure of a repository's contents, and it is a good habit to reach for it rather than `ls`,
because it excludes everything ignored and everything untracked.

Observed on **2026-08-24**:

```text
41
```

Forty-one tracked files: the plan, the addenda, the ledgers, the tooling, the skills, and ten
`.gitkeep` placeholders. **No product code at all** — which is correct, because you have not written
any yet, and every line of it will be typed by you from a day document.

## When it breaks

The failure mode of an empty directory is that it silently does not exist for anyone else:

```bash
mkdir deploy && git add -A && git commit -m "add deploy dir" && git status --short
```

**Line by line:** create a directory, stage everything, commit, then check the state. The chain uses
`&&` so each step only runs if the previous one succeeded
([1.2](../01-the-toolchain/1.2-git-and-the-shell-these-docs-assume.md)).

The commit fails, with:

```text
nothing to commit, working tree clean
```

**What it says:** there is nothing to commit.
**What it actually means:** you created a directory, and **Git does not record directories.** It
records files, and infers directories from their paths. An empty directory is not a thing Git has any
way to represent, so from its point of view you did nothing at all.

**The smallest fix:** put a file in it — `touch deploy/.gitkeep`.

**Why this matters beyond tidiness:** you clone the repository on another machine, or CI checks it
out, and the directory is not there. Then something that writes into it fails with a message about a
path not existing, in a completely different component, at a completely different time. On Day 13,
when CI runs on a fresh checkout for the first time, this is a real and confusing failure — the code
works locally and fails in CI, and the difference is a folder you never noticed you were relying on.

## In production

**What a professional does differently.** They treat the layout as an interface with a stated
rationale, not a preference. A short section in `README.md` or `CLAUDE.md` saying what each directory
is *for* means that "where does this go?" has a written answer, and disagreements are about the
document rather than about taste. Both files in this repository carry that section, and that is why
this part can be short.

**What degrades at scale.** Directory boundaries eventually become **ownership** boundaries, and then
deployment boundaries. A `CODEOWNERS` file mapping directories to reviewers only works if the
directories mean something; a pipeline that rebuilds only what changed only works if "what changed"
maps cleanly onto a component. Teams that never established boundaries end up rebuilding and
redeploying everything on every commit, because they cannot prove what a change affected. **Your
folder layout eventually becomes your deployment granularity**, which is a much bigger deal than it
sounds on Day 0.

**The failure that only shows with real traffic.** Not runtime — organisational, and slower. When the
layout does not match how the system actually decomposes, every change touches several directories,
so every change needs several reviewers, so review latency rises and people start batching changes.
Larger batches mean larger blast radius per deploy and harder attribution when something breaks
(Day 173). This is the mechanism behind the delivery metrics on Day 20: structure shows up in your
deploy frequency long before anyone names it as the cause.

**The review comment a senior engineer leaves.** *"This puts the drift detector in `pulse/`. That
means a bug in monitoring can take down the service it monitors, and they have to be deployed
together. It belongs in `platform_ops/aiops/`."*

**The signal you would alert on.** None — layout is not observable at runtime, and it would be absurd
to page someone about it. But it is **enforceable at review time**, which is the right control for a
structural property: a CI job can assert that no file was added at the repository root, or that
`pulse/` does not import from `platform_ops/`. That second one is genuinely worth having, because it
is the boundary the story in this part exists to protect, and an import is exactly how it gets
violated quietly.

**Blast radius, stated plainly.** Creating directories changes nothing at runtime and nothing outside
the repository. The decision's real blast radius is *future*: a layout that is wrong becomes
progressively more expensive to change, roughly in proportion to how much code has been written into
it. The bound is that today there are ten empty folders and no code, so being wrong right now
costs a `git mv`. **That is exactly why the decision is made today rather than later.**

**Cost:** `0` requests, `0` tokens, `0` meaningful disk — ten empty files.

## Check yourself

```bash
git ls-files | grep -c gitkeep && ls -d */
```

The first counts the placeholders; the second lists every top-level directory. Every directory you
see should have an answer to "what goes here?" that you can state without looking it up.

**Say out loud, without scrolling up:** *why do `pulse/` and `platform_ops/` have to be separate
directories — what specifically goes wrong if the thing that watches the service lives inside the
service?*
