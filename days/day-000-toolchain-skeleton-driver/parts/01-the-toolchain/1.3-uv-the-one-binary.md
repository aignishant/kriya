# 1.3 — `uv`, the one binary

## One-line answer

`uv` is a single program that does all five environment jobs — **fetch the interpreter, create the
environment, resolve compatible versions, write the lockfile, and run your command inside it** — so
there is exactly one answer to "what is installed here?", and that answer is a file you commit.

---

## The story

🎬 **The scene.** A team is trying to work out why a nightly job started failing. The job has not
been touched in seven weeks. The code is identical. The input is identical. The machine is the same
machine.

😬 **The naive fix.** Someone reruns it. It fails the same way. Someone reinstalls everything from
the list of required software the project keeps. It still fails — differently now, which everyone
agrees is worse.

💥 **Why it fails.** The list of required software says the project needs a certain add-on library,
"version 2 or newer". Seven weeks ago, "2 or newer" meant version 2.4. Last Tuesday a version 2.5
was published, and the reinstall obediently fetched it. Version 2.5 renamed one thing. Nobody on the
team chose this; nobody reviewed it; nobody could have seen it in the code, because **the code did
not change — the meaning of the code's requirements changed underneath it.**

💡 **The insight.** "Version 2 or newer" is not a specification. It is a standing instruction to
accept software that did not exist when you wrote it. If you want the same result twice, you must
write down **exactly** what you got the first time — every piece of it, including the pieces you
never asked for by name.

---

## The idea in plain language

Recall the five jobs from [1.1](1.1-why-one-tool-owns-the-environment.md). `uv` does all of them:

| Job | The `uv` command |
| --- | --- |
| Fetch an interpreter of the right version | `uv python install` (and automatically, on demand) |
| Create the project's private environment | `uv sync` (creates `.venv` if absent) |
| Work out a compatible set of library versions | `uv lock`, or automatically inside `uv sync` |
| Write down exactly what was chosen | `uv.lock` |
| Run a command inside that environment | `uv run <command>` |

Two ideas underneath deserve names, because the rest of this curriculum leans on them.

### Direct dependencies versus the transitive closure

**A direct dependency** is a library you asked for by name. `pytest` is one.

**A transitive dependency** is a library your libraries needed. You did not ask for `pluggy`,
`iniconfig`, `packaging`, `pygments` or `colorama` — `pytest` did.

The count matters more than it looks. This project has **two** direct dependencies and **seven**
installed packages. A real ML project has perhaps thirty direct dependencies and three hundred
installed ones. **The transitive set is where reproducibility actually lives**, because it is much
larger than the set you are thinking about, and every one of its members can publish a new version
tomorrow.

### The manifest and the lockfile are different documents

This distinction is the whole point, and it recurs at every scale in this plan:

| | `pyproject.toml` — the manifest | `uv.lock` — the lockfile |
| --- | --- | --- |
| Says | what you **want** | what you **got** |
| Written by | you | `uv` |
| Contains | direct dependencies only | every package, transitive included |
| Records | a name, and a constraint | an exact version **and a hash of the file** |
| Edited by hand? | yes | **never** |
| Committed? | yes | **yes** — this is the part people get wrong |

The hash is the part that turns a wish into a guarantee. It is not merely "install version 0.4.6" —
it is "install the file whose contents produce exactly this fingerprint". A package that is
re-uploaded, tampered with, or corrupted in transit produces a different fingerprint and the install
refuses. **That is a supply-chain control**, and it is why Day 15 (artifacts, reproducibility and the
first SBOM) can build on top of today rather than starting over.

## Why Kriya needs it

Day 23 writes the Dockerfile for `pulse`. A container image is a frozen filesystem, and the most
common way to build one is to copy in a list of requirements and install them at build time. If that
list says "version 2 or newer", **then the image you build in March and the image you build in June
are different software carrying the same tag** — and your rollback (Day 19) rolls back to something
you have never tested.

Day 23 will copy `uv.lock` into the image and install from it precisely so that "rebuild the image"
and "get the same image" are the same sentence.

## The mechanism

Ask `uv` to make reality match the lockfile:

```bash
uv sync
```

**Line by line:** `uv sync` is the workhorse and it does four things in order. It reads
`pyproject.toml` to see what is wanted; it reads `uv.lock` to see what was chosen, re-resolving and
rewriting the lock if the manifest has changed since; it creates `.venv` if it does not exist,
fetching an interpreter matching `requires-python` if needed; and finally it adds and removes
packages until the environment matches the lock **exactly** — including *removing* anything present
that the lock does not mention. That last behaviour is what makes it a *sync* and not an *install*:
the environment is brought to a known state, not merely added to.

Observed on **2026-08-24**, on an already-synced project:

```text
Resolved 8 packages in 1ms
Checked 7 packages in 1ms
```

Two facts hide in those two lines. **`1ms`** — because nothing needed doing; a no-op sync is
essentially free, which is why `./o check` can afford to run through `uv run` every single time
without you noticing. And **8 resolved against 7 checked** — the eighth is the project itself, which
is resolved as a node in the dependency graph but not installed, because `tool.uv.package = false`
tells `uv` this project has no importable code yet
([3.4](../03-repo-skeleton/3.4-pyproject-and-the-lockfile.md) explains why that setting is there and
when it flips).

Now look at what was actually written down:

```bash
head -13 uv.lock
```

**Line by line:** `head -13` prints the first thirteen lines — enough to see the file's header and
one complete package entry without drowning in the other hundred lines. `uv.lock` is committed, so
this is a file every teammate and every CI run reads.

```toml
version = 1
revision = 3
requires-python = "==3.12.*"

[[package]]
name = "colorama"
version = "0.4.6"
source = { registry = "https://pypi.org/simple" }
sdist = { url = "https://files.pythonhosted.org/packages/d8/53/…/colorama-0.4.6.tar.gz", hash = "sha256:08695f5cb7ed6e0531a20572697297273c47b8cae5a63ffc6d6ed5c201be6e44", size = 27697 }
wheels = [
    { url = "https://files.pythonhosted.org/packages/d1/d6/…/colorama-0.4.6-py2.py3-none-any.whl", hash = "sha256:4f1d9991f5acc0ca119f9d443620b77f9d6b33703e51011c16baf57afb285fc6", size = 25335 },
]
```

**Line by line:**

- `version = 1` / `revision = 3` — the format version of the lockfile itself, so a future `uv` knows
  how to read a file written by today's. Every durable format needs this; the ones that omit it
  regret it.
- `requires-python = "==3.12.*"` — the lock is only valid for this interpreter range. A resolution
  is not universal: the correct set of packages genuinely differs between Python versions, so the
  lock records what it was resolved *for*.
- `[[package]]` — the double brackets are TOML's syntax for an array of tables, i.e. "here is another
  item in a list". There is one of these per package, transitive ones included.
- `name` / `version` — an exact version. Not a range. There is nothing to interpret at install time,
  which is exactly the property the story at the top of this page lacked.
- `source = { registry = … }` — *where* it came from. A package can also come from a git URL or a
  local path, and recording which is a supply-chain fact you will want on Day 217.
- `sdist` and `wheels` — the two shapes a Python package ships in: source that must be built, and a
  pre-built archive. Both are recorded because which one gets used depends on the machine.
- `hash = "sha256:…"` — **the guarantee.** A fingerprint of the file's exact bytes. If the downloaded
  file does not produce this fingerprint, the install fails rather than proceeding. This is what
  makes the lockfile a security control and not just a convenience.
- `size` — a second, cheaper integrity signal, and a useful one when you are diagnosing a truncated
  download.

`colorama` is a good example precisely because **nobody asked for it.** It arrived because `pytest`
wanted it on Windows. It is pinned, hashed and recorded anyway — which is the entire point.

## When it breaks

Ask for something that cannot be satisfied, and `uv` refuses rather than guessing:

```bash
uv add "pytest>=999"
```

**Line by line:** `uv add` adds a dependency to `pyproject.toml`, re-resolves the whole graph, and
syncs the environment. Asking for a version that does not exist forces the resolver into a
contradiction on purpose — a deliberate provocation, to see what refusal looks like before you meet
it accidentally. **Run this in a scratch project, not in `ops`**, because `uv add` edits your
manifest.

Observed on **2026-08-24**:

```text
  × No solution found when resolving dependencies:
  ╰─▶ Because only pytest<=9.1.1 is available and your project depends on
      pytest>=999, we can conclude that your project's requirements are
      unsatisfiable.

hint: If you want to add the package regardless of the failed resolution, provide the `--frozen` flag to skip locking and syncing
```

**What it says:** there is no solution.
**What it actually means:** what you asked for cannot be true, and `uv` will not pick something
close on your behalf. Read the explanation itself — *"Because only pytest<=9.1.1 is available and
your project depends on pytest>=999"* — it names both halves of the contradiction. Resolver errors
in this style are readable, which is not something the previous generation of Python installers
could claim, and it is worth slowing down to actually read one rather than skipping to the fix.

**This is the tool working correctly.** The older installers would have installed one version, then
overwritten it with another, leaving an environment that satisfies nobody and reports no error — a
broken state discovered days later, at runtime.

**The smallest fix:** relax the constraint, or accept that two libraries are genuinely incompatible
and choose between them. Either way *you* decide, visibly, in the manifest, in a commit someone can
review.

**Now read the hint underneath**, because it is a trap dressed as help:

> `hint: If you want to add the package regardless of the failed resolution, provide the `--frozen`
> flag to skip locking and syncing`

That flag will make the error go away by **not resolving at all** — writing the dependency into your
manifest without ever checking that it can be installed. There are legitimate uses for it (offline
work, or editing a manifest for a platform you are not on), but reaching for it to silence a conflict
converts a loud build-time failure into a quiet runtime one. **A tool offering you a way to skip its
own check is not the same as that check being optional.**

**The failure you must never "fix" by hand:** editing `uv.lock` to make a conflict go away. The lock
is generated. Hand-editing it produces a file whose hashes no longer match its contents, and the
next `uv sync` on any other machine will fail in a way that looks nothing like the thing you did.

## In production

**What a professional does differently.** In CI they run `uv sync --locked` rather than plain
`uv sync`. The difference is the whole game: plain `uv sync` will happily *update* the lockfile if the
manifest has drifted, so a CI job can silently resolve new versions and test something other than
what you committed. `--locked` **fails** if the lock does not match the manifest.

Be careful which flag you reach for — `--frozen` sounds like the same thing and is not. It installs
from the lock **without checking whether the lock is current**, so it makes the complaint go away
without fixing the drift. `--locked` verifies; `--frozen` assumes.
[3.4](../03-repo-skeleton/3.4-pyproject-and-the-lockfile.md) shows both, with the real output of
each. Day 13 wires `--locked` into the pipeline, and it is the difference between CI testing your
code and CI testing today's internet.

**What degrades at scale.** Resolution time grows with the dependency graph, and an ML project's
graph is enormous — a serving image can carry hundreds of packages and well over a gigabyte before
anyone notices. This is a direct production cost: image size is deploy latency, registry storage and
node disk pressure. Day 24 (multi-stage builds and small images) is where you take it back, and the
first move is always the same — the build environment and the runtime environment do not need the
same packages.

**The failure that only shows with real traffic.** A dependency that is fine everywhere except the
production architecture. A wheel exists for your laptop and not for the container's platform, so the
package is built from source at image-build time — and the version built from source behaves subtly
differently from the pre-built one. The lockfile's separate `sdist` and `wheels` entries exist
because that distinction is real.

**The review comment a senior engineer leaves.** *"`uv.lock` isn't in this PR but `pyproject.toml`
changed. That means CI resolved something we never reviewed. Commit the lock."*

**The signal you would alert on.** None at runtime — but **two gates**, both on Day 13–15: CI fails
if the lockfile is out of date with the manifest, and CI fails if a dependency has a known
vulnerability above your threshold. That second one is a scheduled job as well as a per-commit one,
because a package you installed last month can become vulnerable this month without you touching it.
That is one of the few "your code did not change but your risk did" signals in this whole plan, and
Day 217 handles it properly.

**Blast radius, stated plainly.** `uv` can write to `.venv/`, to `uv.lock`, to `pyproject.toml`, and
to its own cache. It downloads from the package index over the network. Worst case: a malicious or
compromised package executes code at install time — a real attack, not a hypothetical, since
installing a package can run arbitrary code. The bounds you have today are the hash pinning (a
package cannot change under a version you already locked) and review (a new dependency arrives in a
diff someone reads). The bound you do **not** yet have is scanning, which arrives on Day 29.

**Cost:** `0` requests to any model, `0` tokens. Network: one download per new package, cached
afterwards. Disk: this project's `.venv` is small; an ML environment later will be over a gigabyte,
and Day 24 is where that stops being free.

## Check yourself

```bash
uv sync && grep -c "^\[\[package\]\]" uv.lock
```

The second number is how many packages are pinned — count how many you actually asked for in
`pyproject.toml` and notice the gap.
