# 2.2 — `/healthz` — the endpoint that must not lie

## One-line answer

A health endpoint answers exactly one question — *can this process respond?* — and the discipline is
about what it **refuses** to check, because everything you add to it becomes a thing that can take the
whole service down.

---

## The story

🎬 **The scene.** A hospital ward at night. A nurse walks the ward and checks each patient is
breathing. Thirty seconds a bed, all night, every night.

😬 **The naive fix.** A colleague suggests improving it: while you are there, take a full set of
observations. Blood pressure, temperature, bloods sent to the lab. A much better picture.

💥 **Why it fails.** The lab is slow one night. Each check now takes twenty minutes because it waits
for results, so the round takes until morning, so nobody checks whether anyone is breathing. **The
check that was designed to catch the fastest-moving emergency has been made to depend on the
slowest-moving information.** And when the lab goes down entirely, the round does not just slow — it
stops.

💡 **The insight.** The value of the breathing check is not that it is thorough. It is that it is
**fast, cheap and cannot fail for reasons unrelated to the patient**. Those three properties are the
whole design, and every improvement that adds information subtracts one of them. Full observations are
worth taking. They are a different round, on a different schedule, and mixing the two destroys the
useful one.

---

## The idea in plain language

`/healthz` exists so that something other than a human can ask *"is this instance alive?"* and get an
answer in milliseconds. Today nothing asks it. From Day 26 a container runtime does; from Day 41
Kubernetes does, **and acts on the answer by restarting the container**.

That last clause is what makes this endpoint dangerous. A health check is not a report — it is an
input to an automated system with the power to destroy your process. Principle 13 says a capability
arrives with its bound, and the bound on this one is *what the check is allowed to look at*.

### The rule, and the reasoning

**`/healthz` checks that the process can respond, and nothing else.**

Work through the alternative. Suppose it queried the database. The database has a bad afternoon:

1. `/healthz` starts failing — on **every instance simultaneously**, because they all share the
   database.
2. The supervisor concludes every instance is unhealthy.
3. Every instance is restarted. None recovers, because the database is still down.
4. The service, which could have served `/healthz`, cached responses and a clear `503` on the data
   routes, is now **entirely absent**.
5. When the database returns, there is nothing running to notice.

A database outage that should have cost you two routes has cost you everything, and the mechanism that
did it was the health check. **This is the single most common self-inflicted outage in services that
run under an orchestrator**, and it is caused by an endpoint that seemed more useful for being more
thorough.

That reasoning is written down as `ADR-0005`, on
[Day 2](../../../day-002-shape-of-production-system/parts/04-blast-radius/4.4-the-architecture-document-that-survives-you.md),
before this code existed — which is the point of writing decisions down before the code that would
make them awkward to reverse.

### But "the process is up" is not "the service is useful"

This is the honest objection and it is correct. An instance whose database connection is dead answers
`/healthz` with `200` and cannot serve a single `/predict`. The check is not lying — it is answering
its question truthfully and its question is narrow.

The resolution is **two checks with two different consumers**, which is what Kubernetes formalises on
Day 41:

| Question | Name | Who consumes it | What they do about it |
| --- | --- | --- | --- |
| is the process alive? | **liveness** | the supervisor | **restart it** if not |
| can it usefully serve traffic? | **readiness** | the load balancer | **stop sending traffic** if not |

The two actions are completely different and that is why they must be two signals. Restarting a process
because a shared database is slow makes things worse; removing it from the load balancer would too, if
every instance did it at once — but at least nothing is destroyed and recovery is instant.

**Today `pulse` has only the first.** That is deliberate: there is no supervisor and no load balancer,
so a readiness endpoint would have no consumer, and a check with no consumer is not a check
([Day 1, part 1.2](../../../day-001-what-operations-actually-is/parts/01-what-ops-is/1.2-does-it-work-versus-is-it-working.md)).
The second arrives on Day 41 with the thing that reads it.

## Why Kriya needs it

Day 41 is *"Probes — liveness, readiness, startup, and the liveness probe that took production down."*

The title is the incident. On that day you configure Kubernetes to poll this endpoint and to kill the
container when it fails, and the failure lab is a liveness probe that restarts healthy pods during a
slow database query — exactly the cascade above, produced deliberately so you have watched it happen.

## The mechanism

Four lines, and every one of them is a decision.

```python
@app.get("/healthz")
def healthz() -> dict[str, str]:
    """Can this process answer? Nothing else. See ADR-0005."""
    return {"status": "ok"}
```

**Line by line:**

- `@app.get` — `GET`, because this reads and changes nothing. Every health-checking tool in existence
  assumes `GET`, and a `POST` health check would work and surprise everyone
  ([2.1](2.1-the-application-object-and-the-first-route.md)).
- `def` rather than `async def` — but note the reasoning is *stronger* here than for other routes. This
  endpoint must answer even when the service is busy, and a plain `def` runs in a thread pool, so it
  cannot be queued behind a blocked event loop. Day 110 revisits it.
- **No arguments.** A health check that accepts input is a health check that can be made to fail by a
  caller, which is a denial-of-service vector on the endpoint that decides whether your process lives.
- **No dependency call in the body.** The single most important absence in this file. Not the database,
  not the model registry, not the provider. The docstring names the ADR because *this is the line
  somebody will helpfully "improve"*.
- `return {"status": "ok"}` — a constant. It costs no allocation worth measuring, no I/O and no lock.
  **The cost of the check matters**: at a poll every few seconds across many instances, an endpoint
  that does real work is real load, and an endpoint that takes a lock can deadlock the thing it is
  checking.
- An object rather than a bare `"ok"`, for the reason in
  [2.1](2.1-the-application-object-and-the-first-route.md): a JSON object can gain a field later
  without breaking a client that reads `status`.

Run it and look at the whole response, not just the body:

```bash
curl -sS -i http://127.0.0.1:8000/healthz
```

**Line by line:** `-i` includes the response headers in the output. For a health check the headers are
half the information — the status line is what a probe reads, and the body is often ignored entirely.
`-sS` suppresses the progress meter but keeps errors visible, which is the pair you want in any script.

Observed on **2026-08-24**:

```text
HTTP/1.1 200 OK
date: Mon, 24 Aug 2026 09:38:54 GMT
server: uvicorn
content-length: 15
content-type: application/json

{"status":"ok"}
```

**Read the status line first.** `200` is what a probe acts on; most probes never parse the body at all.
Which means the body is for *humans* — the operator running `curl` at 3am — and its job is to say
something a human could not infer from `200`. Today it says almost nothing, honestly, because there is
almost nothing to say.

**`content-length: 15`.** Fifteen bytes. Multiply by a poll every few seconds, by however many
instances, forever. It is negligible here and it is the right instinct: a health endpoint returning a
kilobyte of diagnostics is a design that costs bandwidth and CPU continuously, in exchange for
information nobody reads on the happy path.

## When it breaks

There are two failures worth meeting, and the first is not an error at all.

**The health check that is right and unhelpful.** Observed shape:

```text
$ curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8000/healthz
200
$ curl -sS -i -X POST http://127.0.0.1:8000/predict -H 'content-type: application/json' -d '{"subject":"s","body":"b"}'
HTTP/1.1 503 Service Unavailable
```

**What it says:** the instance is healthy and the endpoint is unavailable.
**What it actually means:** exactly what it says, and both are correct. The process is alive; a
dependency is not. **This looks like a contradiction and is not**, and an operator who expects
`/healthz` to summarise the whole system will read it as a bug in the health check. It is the missing
*readiness* signal, and it is on
[Day 2's blast-radius map](../../../day-002-shape-of-production-system/parts/04-blast-radius/4.2-drawing-the-blast-radius-map.md)
as a known gap with a date.

**The health check that was improved.** Somebody adds a database query. The database goes down, and the
endpoint that is supposed to be the cheapest thing in the service produces:

```text
HTTP/1.1 500 Internal Server Error
content-type: application/json

{"detail":"Internal Server Error"}
```

with this in the log:

```text
Traceback (most recent call last):
  File "/app/pulse/api.py", line 22, in healthz
    db.execute("SELECT 1")
psycopg.OperationalError: connection failed: could not connect to server: Connection refused
        Is the server running on host "db" (172.18.0.3) and accepting TCP connections on port 5432?
```

**What it says:** the health endpoint raised an exception because the database is unreachable.
**What it actually means:** every instance is about to be restarted, none will recover, and a partial
outage is about to become a total one. The traceback is accurate and describes the *second* problem;
the first problem is the line that calls `db.execute` inside a function whose docstring says it checks
nothing else.

**The smallest fix:** delete the dependency call. Not "add a try/except around it and return 200
anyway" — that produces an endpoint that *pretends* to check something, which is worse than one that
honestly checks nothing, because the next person will trust it. **If you want dependency status, that
is a different endpoint with a different consumer** (Day 41).

## In production

**What a professional writes instead of the teaching version.** They give liveness and readiness
genuinely different implementations, and they are strict that **liveness must not depend on anything
external**. The rule of thumb that survives: *if the answer to "should we restart this process?" is
influenced by another machine, the check is wrong.* Restarting fixes a broken process; it never fixes a
broken database, and a check that conflates them turns every dependency outage into a restart storm.

**What degrades at scale.** The cost and the correlation. At three instances, a poll every few seconds
is nothing. At three hundred, the health endpoint is one of the highest-traffic routes in the estate,
and anything it touches is being touched constantly — which is why "just query the database, it's only
a `SELECT 1`" becomes hundreds of connections doing nothing useful. The correlation is worse: every
instance polls the same shared thing, so a shared-dependency blip marks *all* of them unhealthy at the
same instant, and simultaneous is what turns a blip into an outage.

**The failure that only shows with real traffic.** The health check that passes while the process is
useless — a slow memory leak, an exhausted connection pool, a deadlocked worker. The process responds
to `/healthz` because that path allocates nothing and takes no lock, and every real request times out.
This is the genuine cost of the narrow check, and it is worth naming rather than defending: **liveness
is a weak signal and it is the correct signal anyway**, because the alternative failure mode is worse.
The real protection is not a better health check; it is the user-facing SLO on Day 73, which measures
whether requests actually succeed.

**The review comment a senior engineer leaves.** *"This health check now queries the database. When the
database has a bad five minutes, every pod will fail its liveness probe and get killed simultaneously,
and none of them will come back until the database does. Take it out — if you want dependency status,
add `/readyz` and point the readiness probe at it, not liveness."*

**The signal you would alert on.** Not the health check's result directly, which is a subtle point
worth holding. A single instance failing its probe is *normal* — it gets restarted, that is the system
working. What you alert on is: **the fraction of instances that are unhealthy**, which distinguishes a
routine restart from a fleet-wide event, and **the restart rate**, because a process being restarted
repeatedly is `CrashLoopBackOff` and means the restart is not fixing anything (Day 40). Alerting on any
single probe failure produces a page every deploy and is how alert fatigue starts.

**Blast radius.** This endpoint returns a constant and touches nothing, so its own blast radius is
zero. **The interesting blast radius is what it grants to someone else**: from Day 41, a supervisor
uses this endpoint's answer to decide whether to destroy the process. Who can trigger it: the prober,
automatically, with no human involved. What bounds it: the check depends on nothing external, so it can
only report on the thing a restart could actually fix — plus, on Day 41, a `failureThreshold` so a
single blip does not kill anything. **The bound is the narrowness. That is the whole design.**

**Cost:** `0` model calls, `0` tokens. Fifteen bytes and negligible CPU per poll; at a poll every few
seconds that is under a kilobyte a minute per instance, and it never grows.

**The interview question.** *"What does your health check check?"* The answer that lands is short and
then explains the omission: *"only that the process can respond — deliberately. If liveness depends on
the database, a database outage restarts every pod simultaneously and none of them recover. Dependency
status goes in readiness, which the load balancer reads, because 'stop sending traffic' and 'destroy
this process' are different decisions."* Then the honest caveat: a narrow liveness check will pass on a
process that is alive and useless, and the thing that actually catches that is the SLO.

Status and duration. The duration is the number to remember — this endpoint should stay in that range
for the next two hundred days, and the day it does not, something has been added to it.
