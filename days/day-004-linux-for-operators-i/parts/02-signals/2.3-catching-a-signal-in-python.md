# 2.3 — Catching a signal in Python

## One-line answer

Installing a signal handler means telling the kernel "when this number arrives, call this function
instead of doing the default", and in Python it comes with three restrictions that decide whether your
graceful shutdown actually works or only appears to.

---

## The story

🎬 **The scene.** The fire alarm goes off in an office building at eleven in the morning.

😬 **The naive fix.** People who have never been told what to do stand up, look at each other, pick up
their bags and coats, and head for the lift.

💥 **Why it fails.** Everybody knows the alarm is important. Nobody knows what to *do*, so twenty people
crowd into a lift that should not be used, half the floor is still at their desks waiting to see whether
it is real, and the person holding the list of who is in the building has no idea whether anybody is
missing, because there is nowhere agreed to count them.

💡 **The insight.** Knowing that a message is important is worthless without a prepared response. **The
value is entirely in the procedure written down in advance**, while there was time to think, because
the moment the alarm goes off is precisely the moment nobody can think clearly. A handler is that
procedure, written before it is needed.

---

## The idea in plain language

Part [2.1](2.1-what-a-signal-actually-is.md) established the three possible dispositions: default,
ignore, or handler. This part is about arranging the third.

In Python it is one function call. Verified against `docs.python.org/3/library/signal.html` on
**2026-08-24**: `signal.signal(signalnum, handler)` sets the disposition, where the handler is *"a
callable Python object taking two arguments (signal number and stack frame)"*, or one of the two
constants `signal.SIG_IGN` for ignore and `signal.SIG_DFL` to restore the default.

That is the mechanism. The interesting part is the three restrictions around it, because each one is a
production bug waiting to happen.

### Restriction one: handlers do not run where the signal arrives

The Python documentation is explicit, verbatim: *"A Python signal handler does not get executed inside
the low-level (C) signal handler. Instead, the low-level signal handler sets a flag which tells the
virtual machine to execute the corresponding Python signal handler at a later point (for example, at
the next bytecode instruction)."*

Read that carefully, because the consequence is severe and is stated on the same page: *"A long-running
calculation implemented purely in C (such as regular expression matching on a large body of text) may
run uninterrupted for an arbitrary amount of time, regardless of any signals received. The Python
signal handlers will be called when the calculation finishes."*

**So a signal handler in Python is not an interrupt. It is a note left for the interpreter**, actioned
whenever the interpreter next gets a turn. If your process is inside a long C-level call, such as a
large matrix multiplication, a compiled model's inference, or a `re` match over a huge string, the
handler does not run until that call returns. Your graceful shutdown is queued behind exactly the
operation most likely to be slow. This becomes a real constraint from Day 109, when `pulse` starts
calling into compiled inference code.

### Restriction two: only the main thread, and only the main interpreter

Verbatim from the same page: *"Python signal handlers are always executed in the main Python thread of
the main interpreter, even if the signal was received in another thread."* And: *"only the main thread
of the main interpreter is allowed to set a new signal handler."*

There are two consequences. Setting a handler from a worker thread raises `ValueError`. And a main
thread that is blocked, whether waiting on a lock, joining a thread, or sitting in a blocking library
call, cannot run the handler either, because it is busy. **A shutdown handler that never runs because
the main thread is blocked is one of the most common causes of "the container always takes the full
grace period".**

### Restriction three: on Windows, most of them do not exist

Also verbatim: *"On Windows, signal() can only be called with SIGABRT, SIGFPE, SIGILL, SIGINT, SIGSEGV,
SIGTERM, or SIGBREAK. A ValueError will be raised in any other case."*

This matters directly to you today, because this project runs on Windows until WSL2 arrives on Day 21,
as Addendum 02 says. `SIGTERM` and `SIGINT` are available, which covers everything in this section.
`SIGHUP`, which is the conventional "reload your configuration" signal you will want on Day 68, is
**not**, and code that installs a `SIGHUP` handler will raise on this machine and work on the server.
Guarding for it is not defensive over-engineering. It is the difference between code that runs in both
places and code that does not.

### What a handler should actually do

Almost nothing. The disciplined pattern is: **set a flag, and return.**

The reason is that a handler runs at an arbitrary point in your program's execution, between two
bytecode instructions that might be in the middle of anything. Doing real work there, such as writing
files, acquiring locks or making network calls, means doing it from an unknown state. Setting a boolean
and letting the normal flow of the program notice it is safe, predictable and testable.

The exception is when your framework has already built the machinery, which is the case for uvicorn and
is what part [4.1](../04-the-service-died/4.1-graceful-shutdown-for-pulse.md) uses.

## The mechanism

Write the smallest honest handler, in the day's lab folder rather than in `pulse/` yet.

```python
# days/day-004-linux-for-operators-i/lab/handler.py
import signal
import sys
import time
from types import FrameType

stopping = False


def on_signal(signum: int, frame: FrameType | None) -> None:
    """Record that a stop was requested. Do nothing else here, deliberately."""
    global stopping
    stopping = True
    print(f"[handler] caught {signal.Signals(signum).name} ({signum})", flush=True)


signal.signal(signal.SIGTERM, on_signal)
signal.signal(signal.SIGINT, on_signal)

print(f"[main] pid={__import__('os').getpid()} working; send TERM or INT", flush=True)

while not stopping:
    time.sleep(0.2)

print("[main] draining: finishing in-flight work", flush=True)
time.sleep(1)
print("[main] clean exit", flush=True)
sys.exit(0)
```

**Line by line:**

- `import signal` brings in the standard-library module. There is nothing to install, because this has
  been in Python forever.
- `stopping = False` is the flag. This, rather than the handler, is where the shutdown decision actually
  lives.
- `def on_signal(signum: int, frame: FrameType | None) -> None:` takes the two arguments the
  documentation requires: the signal number, and the stack frame that was executing when it arrived. You
  will almost never use `frame`, because it is there for debuggers. It is typed because this repository
  types public functions, as `CLAUDE.md` says, and `FrameType | None` is the honest type, since the
  frame can be `None`.
- `global stopping` is required, because assigning to a name inside a function otherwise creates a local
  one. Leaving it out is the classic version of this bug: the handler runs, prints its message, sets a
  *local* variable, returns, and the loop never stops. **The symptom is a process that logs "caught
  SIGTERM" and then keeps running**, which looks like a signal problem and is a scoping problem.
- `signal.Signals(signum).name` turns `15` into the string `SIGTERM`, using the `IntEnum` the
  documentation describes. Logging the name rather than the number is worth the character count, because
  `15` in a log tells a future reader nothing and `SIGTERM` tells them everything.
- `flush=True` on every print is **not optional here.** Python buffers standard output when it is not a
  terminal. A process that is about to exit, or about to be hard-killed, may never flush that buffer, so
  the most important log lines in the process's life are exactly the ones most likely to be lost. This
  is the same lesson as `SIGKILL` losing buffered writes, from
  [2.2](2.2-sigterm-and-sigkill-the-request-and-the-order.md), and Day 67 makes it a permanent rule for
  `pulse`.
- `signal.signal(signal.SIGTERM, on_signal)` installs it. There are two calls because `SIGTERM`, which
  is a manager stopping you, and `SIGINT`, which is a human pressing `Ctrl-C`, should behave
  identically, and a process that handles one and not the other behaves differently in development and
  in production for no good reason.
- `while not stopping: time.sleep(0.2)` is the work loop, standing in for a server. It uses `sleep`
  rather than a busy loop, because a busy loop would consume a full core, from
  [1.4](../01-the-process/1.4-process-states-and-the-d-that-will-not-die.md), and teach nothing extra.
  The `0.2` bounds how long after the signal the loop notices, so it is the granularity of your
  shutdown.
- `time.sleep(1)` in the drain stands in for finishing real in-flight requests. This is the part that
  has to fit inside the grace period, from [2.2](2.2-sigterm-and-sigkill-the-request-and-the-order.md).
- `sys.exit(0)` exits deliberately, with a code that says "I was asked to stop and I did". Section
  [3](../03-exit-codes/3.1-the-exit-code-is-the-whole-return-value.md) is why that line is not a
  formality.

Run it and stop it.

```bash
uv run python days/day-004-linux-for-operators-i/lab/handler.py &
HP=$!
sleep 1
kill -TERM "$HP"
wait "$HP"
echo "exit code: $?"
```

**Line by line:** this is the same start-capture-signal-wait shape as
[2.2](2.2-sigterm-and-sigkill-the-request-and-the-order.md), so that the only variable is the program.

Observed on **2026-08-24**:

```text
[main] pid=32188 working; send TERM or INT
[handler] caught SIGTERM (15)
[main] draining: finishing in-flight work
[main] clean exit
exit code: 0
```

**Four lines that did not exist before you wrote the handler.** Compare that with the same program
before `signal.signal` was called: the kernel's default action would have terminated it instantly,
printing nothing, and the exit code would have been `143`.

### Proving restriction one is real

This is the experiment worth doing, because the restriction sounds theoretical until you watch it.

```python
# days/day-004-linux-for-operators-i/lab/blocked_handler.py
import re
import signal
import sys

stopping = False


def on_signal(signum: int, frame) -> None:
    global stopping
    stopping = True
    print(f"[handler] caught {signal.Signals(signum).name}", flush=True)


signal.signal(signal.SIGTERM, on_signal)
print(f"[main] pid={__import__('os').getpid()} entering a long C call", flush=True)

# A pathological pattern: this is one call into the C regex engine and it takes a long while.
re.match(r"(a+)+b", "a" * 40)

print(f"[main] C call finished; stopping={stopping}", flush=True)
sys.exit(0)
```

**Line by line:**

- `re.match(r"(a+)+b", "a" * 40)` is a deliberately catastrophic pattern. The nested quantifier makes
  the regex engine try an exponential number of ways to match, and against forty `a` characters with no
  `b` it will not finish for a very long time. **This is one call**, entirely inside the compiled regex
  engine, so the interpreter never gets a turn.
- Everything else is the same handler as before, so the only difference between this program and the
  working one is *what the main thread is doing when the signal arrives*.
- The final `print` reports the flag's value **after** the call returns, which is what shows you when
  the handler actually ran.

```text
$ uv run python days/day-004-linux-for-operators-i/lab/blocked_handler.py &
[1] 32240
[main] pid=32240 entering a long C call
$ kill -TERM 32240
$
```

**Nothing happens.** There is no `[handler] caught SIGTERM` line. The process sits there. `ps` shows it
as `R`, burning a core, ignoring you, and it is not ignoring you, it is *unable to notice you*, because
the interpreter has not executed a bytecode instruction since before you pressed enter.

```text
$ ps -o pid,stat,%cpu,args -p 32240
    PID STAT %CPU COMMAND
  32240 R    99.2 python days/day-004-linux-for-operators-i/lab/blocked_handler.py
```

**The only way out is `SIGKILL`**, which is not delivered to the process at all and therefore does not
care what the interpreter is doing.

```bash
kill -KILL 32240
```

**Line by line:** this is the uncatchable signal from
[2.2](2.2-sigterm-and-sigkill-the-request-and-the-order.md), used here for its actual legitimate
purpose, which is a process that genuinely cannot respond. Note the asymmetry it demonstrates: **the
escape hatch works precisely because it does not involve the process.**

```mermaid
sequenceDiagram
    participant K as kernel
    participant C as C-level handler
    participant V as Python VM
    participant H as your handler()
    K->>C: SIGTERM arrives
    C->>C: set a flag. return immediately.
    Note over C,V: nothing of yours has run yet
    alt VM is executing bytecode
        V->>H: next instruction boundary → call handler()
        H->>H: stopping = True; return
        Note over V: loop notices the flag, drains, exits 0
    else VM is inside a long C call
        Note over V: no instruction boundary happens
        Note over H: handler() is not called.<br/>process appears to ignore the signal.
        K-->>V: only SIGKILL ends this
    end
```

## When it breaks

**`ValueError: signal only works in main thread of the main interpreter`.** You tried to install a
handler from a worker.

```text
Traceback (most recent call last):
  File "/app/worker.py", line 18, in run
    signal.signal(signal.SIGTERM, self._on_signal)
  File "/usr/lib/python3.12/signal.py", line 58, in signal
    handler = _signal.signal(_enum_to_int(signalnum), _enum_to_int(handler))
              ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
ValueError: signal only works in main thread of the main interpreter
```

**What it says:** exactly what it says.

**What it actually means:** you have put shutdown logic in the wrong place. This is common when somebody
wraps their service in a class and installs handlers in the class's `start()` method, which is then
called from a thread.

**The smallest fix:** install the handler at module level or in `main()`, on the main thread, and have
it set a flag or a `threading.Event` that the workers can read. The handler stays in one place, and the
reaction is distributed.

**`AttributeError` for `SIGHUP` on Windows.** This is the one that will bite you on this machine.

```text
Traceback (most recent call last):
  File "reload.py", line 7, in <module>
    signal.signal(signal.SIGHUP, on_reload)
                  ^^^^^^^^^^^^^
AttributeError: module 'signal' has no attribute 'SIGHUP'
```

**What it says:** `SIGHUP` does not exist here.

**What it actually means:** you are on Windows, where the documented list is `SIGABRT`, `SIGFPE`,
`SIGILL`, `SIGINT`, `SIGSEGV`, `SIGTERM` and `SIGBREAK` and nothing else. Note that it is an
`AttributeError` on the constant rather than a `ValueError` from `signal()`, because the name is not
even defined.

**The smallest fix:** guard it.

```python
if hasattr(signal, "SIGHUP"):
    signal.signal(signal.SIGHUP, on_reload)
```

**Line by line:** `hasattr` asks whether this platform's `signal` module defines the name at all, which
is the correct question, because checking `sys.platform` would work today and break on the next
platform. Portable code that needs `SIGHUP` behaviour on Windows uses a different mechanism entirely, a
file watch or an admin endpoint, and Day 68 makes that choice explicitly rather than pretending the
signal exists.

**The handler that logs and does not stop.** This is the scoping bug, and it looks like a kernel
problem.

```text
[handler] caught SIGTERM (15)
[handler] caught SIGTERM (15)
[handler] caught SIGTERM (15)
```

It repeats, with the process still running.

**What it says:** the signal is being caught, repeatedly.

**What it actually means:** the handler works perfectly and the flag it sets is a local variable, because
`global stopping` was left out. The loop reads the module-level `stopping`, which is still `False`.
**Every layer is behaving correctly and the program does not stop.**

**The smallest fix:** add `global stopping`, or, better, use a `threading.Event`, because `event.set()`
changes an object rather than rebinding a name, so the whole class of bug disappears. That is why
production code tends to use an `Event` even in single-threaded programs.

## In production

**What a professional writes instead of the teaching version.** They do not hand-roll this at all for a
web service, because the framework already has it. Uvicorn installs `SIGTERM` and `SIGINT` handlers and
exposes lifecycle hooks, which is what part
[4.1](../04-the-service-died/4.1-graceful-shutdown-for-pulse.md) uses. Hand-rolling is for the things
frameworks do not cover: batch jobs, workers pulling from a queue, training runs and agent loops. There
the pattern is always the same, which is a `threading.Event` set by the handler, checked between units
of work, with a hard deadline so that "draining" cannot become "hanging".

**What degrades at scale.** Handler latency becomes visible. The `0.2` second poll in the loop above is
invisible with one process, and it is a fifth of a second added to every instance's shutdown, and across
a large rolling deploy that is real wall-clock time. More importantly, the *granularity* of the check
determines your worst case. A worker that checks the flag once per job, with jobs that take a while,
will always overrun a short grace period, no matter how correct the handler is. **The fix is to make the
unit of work smaller rather than the grace period longer.**

**The failure that only shows with real traffic.** Restriction one, exactly. In development every call
is fast, the interpreter gets a turn constantly, and handlers fire instantly. In production under load
the process spends most of its time inside compiled library code, whether that is a model's forward
pass, a compression routine or a database driver, and the handler's response time becomes the duration
of whatever C call happened to be running. The symptom is shutdown that is instant nine times out of ten
and occasionally takes the full grace period, with no pattern anybody can see. It correlates with load
rather than with code.

**The review comment a senior engineer leaves.** *"This handler does the draining work inline, because it
closes the database pool and writes a final metrics flush from inside the signal handler. That runs at
an arbitrary bytecode boundary, so it can execute while the main code is halfway through a transaction.
Set an event and let the main loop do the work. The handler should be three lines."*

**The signal you would alert on.** The new signal this part introduces is **shutdown duration**, which is
the time between receiving `SIGTERM` and the process actually exiting. Emit it, and alert when it
approaches the configured grace period, because that is your early warning that the next slightly slower
shutdown will be a hard kill and a batch of dropped requests. This is a much better signal than alerting
on the hard kill itself, which tells you about damage already done. You would **not** alert on individual
handler invocations.

**Blast radius.** Installing a handler is a real capability change, because **you are taking over a
decision the kernel was making correctly on its own.** The worst case is a handler that catches
`SIGTERM` and then hangs, waiting on a lock, on a network call with no timeout, or on a queue that is
empty, which converts a service that stopped instantly into one that cannot be stopped politely at all,
so that every stop becomes a grace-period wait followed by a hard kill. Anybody who can stop the process
can trigger it, which is every deploy. What bounds it is putting a hard deadline inside the drain, and
never making a network call from a shutdown path without a timeout, which is Day 7, section 4. **A
shutdown handler with an unbounded wait in it is strictly worse than no handler at all**, because the
default action at least worked.

**Cost.** `0` model calls, `0` tokens, `0` CI minutes and `0` disk. A handler costs a few bytes and one
function call per signal. **The `blocked_handler.py` experiment costs one full processor core** for as
long as you leave it running, and on this four-core machine that is a quarter of the machine, so kill it
when you are done and do not walk away from it.

**The interview question.** *"Your Python service does not shut down cleanly under Kubernetes even
though you handle `SIGTERM`. Where do you look?"* The answer that lands lists the three restrictions:
*"First, whether the handler is installed on the main thread, because Python only allows it there, and a
class that installs it from a worker raises. Second, whether the main thread is actually free to run it,
because Python handlers run between bytecode instructions, so if the process is inside a long compiled
call, whether that is inference, a regex or a native library, the handler is queued until that returns.
Third, whether the process is even PID 1 in the container, because if the entrypoint is a shell then the
signal never reaches Python at all. Then I would check the obvious one, which is whether the handler
sets a flag that something actually reads."*
